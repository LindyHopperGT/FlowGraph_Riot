## What this is

The exact text grammar Courier uses to export/import Flow graphs
(`export_flow_asset` / `import_and_regraph_flow_asset`). This is copied
directly from the glossary's own embedded format guide so agents don't need a
live editor call just to learn the grammar - **fetch this article first**
before writing or parsing Courier text.

## File Structure

```
FlowGraphExport v1.0
WorldBound: true/false
ExpectedOwnerClass: None or /Script/Module.ClassName
---

[NODES]
Node: GUID
  Type: /Full/Path/To/NodeClass
  Properties:
    PropertyName: value
  InputPins:
    - PinName [PinType]
  OutputPins:
    - PinName [PinType]
---

[CONNECTIONS]
SourceGUID.SourcePin -> TargetGUID.TargetPin
---
```

## Property Format Rules (CRITICAL)

Unreal Engine uses a specific property text format. **Do not use JSON syntax.**

- **Arrays:** `(element1,element2,element3)` - parentheses, no spaces after commas. Not `[element1, element2, element3]`.
- **Structs:** `(Field1=Value1,Field2=Value2)` - `=` for assignment, parentheses not braces. Not `{Field1: Value1, Field2: Value2}`.
- **Array of structs:** `((Field1=Val1,Field2=Val2),(Field1=Val3,Field2=Val4))` - outer parens for the array, inner parens per struct.
- **TInstancedStruct** (e.g. `DataPinValue`): `PropertyName=/Script/Module.StructType(Field1=Value1,Field2=Value2)` - must use the **full struct path** (`/Script/Flow.FlowDataPinValue_Text`), never the short name (`FFlowDataPinValue_Text`).
- **NamedProperties example** (`FlowNode_DefineProperties`):
  ```
  NamedProperties: ((Name="PropName",DataPinValue=/Script/Flow.FlowDataPinValue_Text(Values=("text value"))))
  ```
- **Common property types:** Boolean `true`/`false` (lowercase); Integer `42`; Float `3.14`; String `"quoted text"`; Name `UnquotedName`; Text (`FText`) `"quoted text"`; Text (`FFlowDataPinValue_Text`) `(Values=("quoted text"))` - **must use the `Values` array wrapper**; Object reference `/Full/Path/To/Asset.Asset`; Enum `EnumValueName`.

## Pin Declaration

- **Exec pins:** `- PinName [Exec]`
- **Data pins:** `- PinName [TypeName]` (e.g. `[Text]`, `[Vector]`, `[Int]`)
- Dynamic data pins are created automatically when referenced in connections.

## Connection Format

- **Format:** `SourceNodeGUID.SourcePinName -> TargetNodeGUID.TargetPinName`
- Works for both exec and data pins. Pin names are case-sensitive.

## AddOn Format

AddOns are instanced sub-objects that extend a node's behavior. They appear inside a node block, after its pins:

```
Node: <GUID>
  Type: /Game/Path/To/FN_SomeNode.FN_SomeNode_C
  Properties:
    SomeProperty: value
  AddOn: /Game/Path/To/FNA_SomeAddOn.FNA_SomeAddOn_C
    AddOnProperty: value
  AddOn: /Game/Path/To/FNA_AnotherAddOn.FNA_AnotherAddOn_C
    AnotherProperty: value
```

- Each `AddOn:` line starts a new addon block scoped to the current node.
- Addon properties are indented with 4 spaces (same rules as node properties).
- Multiple addons can attach to a single node - each gets its own `AddOn:` line.
- The class path must be the full Blueprint-generated class path ending in `_C`.

## Property Values vs Pin Connections

**Prefer setting property values directly on nodes whenever possible.**

- **Direct property value (preferred):** use when the value is known at design time, is constant, or is simple.
- **Pin connection:** use when the value is computed/generated by another node, is dynamic, or must be passed between nodes as part of the flow logic.

## Connection Topology Rules (CRITICAL)

**One output pin can only connect to one input pin.** The importer silently drops any connection that would assign a second target to an already-connected output pin.

**Wrong** - fan-out from a single output pin:
```
A.OnInteracted -> B.Increment
A.OnInteracted -> C.In        <- silently dropped; A.OnInteracted already has a target
```

**Correct** - use an intermediate `ExecutionSequence` to fan out:
```
A.OnInteracted -> FAN.In
FAN.0 -> B.Increment
FAN.1 -> C.In
```

**`ExecutionSequence` output pin count is fixed by the CDO** - exactly 2 output pins (`0` and `1`). Declaring or connecting a third pin (e.g. `2`) is silently ignored.

**Correct** - chain a second `ExecutionSequence` for a third branch:
```
SEQ_A.0 -> X.Spawn
SEQ_A.1 -> SEQ_B.In
SEQ_B.0 -> Y.Spawn
SEQ_B.1 -> Z.Spawn
```

## Common Mistakes to Avoid

| Wrong | Correct |
|---|---|
| `NamedProperties: [{PropertyName: "Name", PinType: {PinCategory: "text"}}]` | `NamedProperties: ((Name="Name",DataPinValue=/Script/Flow.FlowDataPinValue_Text(Values=("value"))))` |
| `MyArray: [1, 2, 3]` | `MyArray: (1,2,3)` |
| `DataPinValue=(FFlowDataPinValue_Text,Values=("text"))` | `DataPinValue=/Script/Flow.FlowDataPinValue_Text(Values=("text"))` |

## Glossary markdown structure (for parsing glossary output, not Courier text)

Distinct from the grammar above: the **glossary** (`ExportGlossaryToString()`) uses its own markdown structure, confirmed via a live export:
- Node/addon entries are headed `## ClassName` (not `###`).
- Each entry has `**Class:**`, `**Category:**`, `**Description:**`, optional `**Keywords:**` / `**Dynamic Pins:**`, then `### Properties` (a table, or `*No editable properties*`), `### Input Pins` (a table, or `*No input pins*`), `### Output Pins` (a table, or `*No output pins*`).
- Entries are separated by a `---` line.
- The "Flow Asset Types" section (`## Flow Asset Types` -> `### AssetClassName` sub-headings) is one level lower than node/addon entries.
